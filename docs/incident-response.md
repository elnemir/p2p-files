# Реагирование на инциденты

## Контекст и границы
Runbook относится к реализованному эксплуатационному контуру FileX. PostgreSQL содержит authoritative metadata, Local/S3 — ciphertext, bootstrap KEK хранится отдельно. Потеря metadata, ключей и payload имеет разные способы восстановления. Контур, API и точные JSON inputs: [recovery runbook](../wiki/operations-recovery.md), [CLI](cli.md), [ключи](key-management.md). Локальные drills подтверждены в [development](../wiki/development.md); инфраструктурное disaster recovery и production acceptance остаются фазой 7.

## Общий поток: сигнал → ограничение → доказательства → восстановление
1. Зафиксировать UTC-время, symptom/errorCode, ID операции/инцидента и затронутый provider или account без секретов. Источники: приватная ADMIN панель, `operations status`, `incidents list`, internal metrics. Публичный status не содержит forensic context.
2. При подозрении на нарушение целостности или неконтролируемый доступ закрыть gate через `recovery close` с причиной. Сервис прекращает data plane; работающие handlers/tasks отменяются, exclusive recovery ждёт их завершения. Потеря PostgreSQL сама блокирует доступ, но в недоступную БД нельзя записать gate/incident.
3. Сохранить доступные encrypted backup, JSON/PDF incident revisions, audit evidence и checkpoints во внешнем защищённом хранилище. Не менять повреждённые строки и не удалять orphan objects ради «чистого» отчёта. Backup исключает payload и KEK: их независимую копию хранит оператор.
4. Выполнить соответствующую процедуру ниже. Restore всегда создаёт и проверяет pre-backup; KEK rewrap/restore меняют generation и требуют restart всех API/worker. При ошибке gate остаётся закрытым; автоматического отката или reopen нет.
5. После устранения причины выполнить audit/crypto/storage reconciliation, проверить findings/capabilities, разрешить подтверждённые incidents и явно открыть gate по свежему report ID/hash. Изменение capabilities/административных данных требует повторной сверки.

## Сценарии

| Сигнал и затронутые данные | Немедленное действие и восстановление | Проверка и ограничение |
|---|---|---|
| Утечка API token или recipient link | Отозвать конкретную capability штатным owner/ADMIN действием; при неизвестном масштабе закрыть gate и выполнить `recovery revoke-capabilities`. Сохранить сведения об отзыве. | Старый token/link должен отклоняться. Глобальный revoke отзывает все links/API tokens и инвалидирует reconciliation; после restore старые capabilities могут вернуться из backup. |
| Компрометация ADMIN account/session | С доверенного host закрыть gate; другим доверенным ADMIN отозвать сессии, ограничить скомпрометированный account, проверить settings/storage/key changes и административный audit. | Проверить невозможность входа/чтения старой сессией. Если затронут host или KEK, одного session revoke недостаточно; нужна независимая проверка инфраструктуры. |
| Утрата или компрометация KEK | При наличии доверенного текущего KEK выполнить `kek rewrap` с новым ключом через stdin и проверенным pre-backup, обновить bootstrap secret, restart/reconcile. При утрате использовать отдельно сохранённый исторический KEK для matching backup. | Без нужного KEK ciphertext не восстанавливается. Rewrap не отзывает уже скопированные ключи/данные злоумышленника; historical backups по-прежнему требуют historical KEK. Host recovery/escrow — операторская граница. |
| Local/S3 недоступен, degraded provider или stuck deletion | Проверить private storage findings и инфраструктурную доступность; закрыть gate при неизвестной целостности, сохранить object IDs/errorCode. Восстановить доступ либо использовать штатные drain/migration/check после проверки. | Не переключать metadata на пустое хранилище. Deletion повторяется идемпотентно, но freeze/forensic удержание намеренно запрещает удаление. Реальные provider credentials/endpoints требуют отдельной проверки. |
| `integrity_failed` / `storage_missing` | Сохранить private incident evidence; при необходимости установить hold и получить forensic данные через reason/reauth/audit. Восстановить исходные bytes из независимой копии и выполнить ADMIN check. | Доступ остаётся закрытым для файла до проверки исходного SHA/AEAD. Нельзя менять expected checksum ради принятия повреждённых bytes. Copy metadata не восстанавливает удалённый payload. |
| Audit-chain corruption | Автоматический critical incident закрывает gate. Сохранить повреждённые строки, `audit evidence` и внешний checkpoint; установить причину. Создать recovery checkpoint с текущим combined evidenceHash и объяснением. | Повторить `audit verify`, разрешить incident, reconcile/reopen. Повреждённый prefix сохраняется; последующее его изменение обнаруживается. Новый checkpoint не доказывает подлинность уже повреждённой истории. |
| Crypto-health failure | Gate закрывается до попытки записи encrypted incident report. Восстановить читаемые ключи/конфигурацию из доверенного источника или выполнить verified restore. | При повреждении configuration key сам report может быть недоступен. Reopen запрещён до успешной crypto проверки; восстановление пустыми ключами не является ремонтом. |
| Потеря PostgreSQL / Redis | Для PG подготовить matching binary/schema, новый master KEK, импортировать trusted backup с historical recoveryKEK и выполнить полный restore flow. Redis можно пересоздать как ephemeral service. | Verify archive → mandatory pre-backup → atomic restore → restart → reconcile → review/reopen. Redis не содержит authoritative очередей; потеря PG не компенсируется Redis. Production RPO/RTO пока не измерены. |
| SMTP/webhook outage или DLQ | Сохранить delivery ID/state/lastCode, проверить ADMIN transport configuration и provider; после устранения выполнить штатный retry/resend нужных deliveries. | Publish не означает доставку письма. Webhook receiver должен deduplicate stable eventId; повтор может реально отправить сообщение. После restore pending deliveries отменены и сами не переотправляются. |
| Orphan payload/artifact или incomplete backup | Сохранить reconciliation inventory/findings; сопоставить с pre-backup и логом операций. Incomplete descriptor/chunks не использовать для restore. | Orphans автоматически не публикуются и не удаляются. Cleanup обычных просроченных staging/artifacts не заменяет расследование orphan inventory. Любое ручное удаление требует отдельного решения владельца данных. |

## Пример восстановления повреждённого audit
`audit verify` создаёт incident и закрывает gate → `audit evidence` даёт evidenceHash → оператор сохраняет этот hash, повреждённую историю и внешний anchor → `audit checkpoint` с `kind=recovery`, причиной и этим hash → повторный `audit verify` → `incidents update` в resolved → `recovery reconcile` → проверка report → `recovery reopen`. Между evidence и checkpoint новые изменения журналов требуют заново получить evidenceHash. JSON схемы команд — в [CLI](cli.md).

## Evidence, коммуникация и ограничения
Incident JSON revisions зашифрованы в БД и не имеют TTL/user purge; PDF строится из выбранной revision, header SHA-256 относится к JSON. ADMIN access не уведомляет владельца автоматически. Внешнее уведомление об инциденте, состав получателей и допустимое раскрытие forensic данных определяет оператор; автоматической отправки сообщений из этого runbook нет.

Audit HMAC/checkpoints в той же БД не противостоят одновременной компрометации host+DB+keys и полному rollback без независимых anchors. Pre-backup сохраняет возможность расследования/последующего восстановления, но не выполняет автоматический rollback. Повторный restore проходит те же guards. Ни resolving incident, ни reopen не принимают production residual risks.
