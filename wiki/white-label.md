# Настраиваемый брендинг

## Контекст и задача
Брендинг — общее оформление одной установки. ADMIN меняет название продукта, палитры, иконки и изображения без пересборки приложения. Настройки действуют для всех пользователей и анонимных страниц; отдельных брендов по пользователю или домену нет. Решение и security/crypto review: [ADR-013](adr/013-white-label.md).

## Как настроить
1. Войти как ADMIN, открыть **Администрирование → Оформление → Брендинг и оформление**. Для сохранения требуется подтверждение пароля за последние пять минут; «Подтвердить личность» доступно прямо над разделами ADMIN. Также доступно в «Настройки → Аккаунт и безопасность».
2. Указать название, описания на русском и английском и необязательную подпись внизу страниц.
3. Выбрать тему по умолчанию (системная, светлая, тёмная), стиль иконок (контурный, скруглённый, двухтоновый). Переключатели темы/языка доступны после загрузки клиентского интерфейса, чтобы ранний выбор не потерялся при hydration. Личная настройка темы в шапке имеет приоритет; вариант наследования возвращает выбор администратора.
4. Загрузить светлый/тёмный логотип и favicon. Если задан только один логотип, он используется в обоих режимах; без логотипов выводится название.
5. Выбрать готовую палитру или настроить девять цветов каждого режима. Проверить оба предпросмотра. Изменения черновика не видны остальным пользователям.
6. Нажать **Применить брендинг**. Новая ревизия сохраняется целиком; вкладки получают обновление сразу при сигнале, при возврате фокуса или в течение минуты для активной вкладки.

Черновик хранится только в открытом редакторе: перезагрузка или переход на другую вкладку разделов приложения его сбрасывает. Если редактирование заняло больше пяти минут, подтвердите пароль в настройках **во второй вкладке того же браузера**, затем вернитесь к редактору и сохраните. Это обновляет ту же сессию и сохраняет черновик на экране.

**Исходное оформление** подставляет FileX в черновик; для публикации сброса нужен отдельный клик «Применить». **Отменить изменения** загружает текущую сохранённую версию. При конфликте двух администраторов черновик остаётся на экране, но повторное применение требует загрузить актуальную ревизию и перенести нужные изменения. История ревизий не редактируется.

## Поля и ограничения
| Поле | Правило |
|---|---|
| Название | 1–80 Unicode символов, без управляющих/невидимых символов и пробелов по краям |
| Описания, подпись | До 160 символов, обычный текст; HTML не исполняется |
| Светлая/тёмная палитра | Фон, текст, вторичный текст, карточки, границы, акцент, текст на акценте, текст/фон ошибки; только #RRGGBB |
| Контраст | Текст/вторичный текст/акцент к фону и карточке ≥4.5:1, границы ≥3:1, текст на акценте и ошибки ≥4.5:1 |
| Изображения | PNG/JPEG, каждый файл ≤128 KiB; логотип ≤1024×512 px, favicon ≤256×256 px |
| Загрузка | Проверка содержимого, размеров и декодирования; повторное кодирование в 8-bit PNG удаляет metadata и посторонние chunks |
| Запрос | Полный JSON ≤600 KiB; URL, SVG, произвольный CSS/JS и неизвестные поля запрещены |

Пример: «Acme Share», описание «Документы вашей команды», палитра «Океан», скруглённые иконки и два логотипа. Favicon отображается во вкладке браузера и используется как иконка новых browser notifications. Произвольная замена отдельных SVG-иконок не предусмотрена: выбирается согласованный набор из трёх стилей.

## Поток данных и компоненты
ADMIN draft → строгая проверка API → нормализация изображений → PostgreSQL CAS и audit в одной transaction → публичная ревизия → Next.js SSR/context → CSS variables, логотипы, иконки, title и favicon.

`internal/branding/defaults.json` — единый исходный бренд Go и TypeScript. `internal/branding` валидирует и хранит ревизии; `BrandingProvider`, `BrandingPanel`, `Brand`, `Icon` в `apps/web/components` применяют оформление. Migration **0018** создаёт `branding_revisions` и immutable presentation snapshots отчётов. Сбой записи аудита откатывает публикацию. Текущие роль, session epoch, revoke, срок сессии и reauth повторно проверяются под transaction locks. Номера ревизий монотонны, но могут иметь пропуски после rollback.

- `GET /api/v1/branding` — публичный `{revision,value}`, ETag/304, без actor/history/settings/secrets.
- `GET /api/v1/admin/branding` — административное чтение.
- `PUT /api/v1/admin/branding` — полный `{expectedRevision,value}`, ADMIN session, Origin/CSRF и свежий reauth; bearer запрещён. 400 — неверное значение, 403 — недостаточная авторизация, 409 — устаревшая ревизия.

Полные модели и security: [OpenAPI](../contracts/openapi.json), [branding-v1 schema](../contracts/schemas/branding-v1.json). Settings v1 и AsyncAPI не меняются. Публичные имена и изображения не должны содержать секретов: они намеренно доступны до входа.

## Где применяется и что сохраняется
Оформление покрывает вход, кабинет, получателя, помощь, статус и проверку отчётов. Название используется в browser notifications, SMTP subject/body/display name и WebDAV root display name. Адрес отправителя остаётся из SMTP configuration. Unicode subject кодируется MIME Base64, чтобы максимальное имя не превышало SMTP line limit. Письмо берёт текущий бренд при попытке доставки; ранее доставленные письма не переписываются.

Новый отчёт фиксирует бренд одновременно с созданием revision, отдельно от canonical JSON. PDF использует сохранённое название/светлый логотип/акцент; последующее изменение бренда не меняет выпущенный отчёт. Бумага PDF остаётся белой: если выбранный акцент недостаточно контрастен к белому, название выводится чёрным. Legacy rows с NULL используют прежний renderer. JSON/schema/hash, privacy и криптографические форматы не меняются; artifact hash связывает байты PDF. То же правило snapshot действует для security incident reports. Логическое backup/restore переносит ревизии и snapshots вместе с БД.

WebDAV authentication realm теперь нейтральный `WebDAV` и не меняется при последующих сменах бренда; после обновления клиент с сохранённым прежним realm может один раз запросить пароль подключения заново.

Технические идентификаторы `filex-verify`, WebDAV username `filex`, cookies, localStorage и protocol headers сохраняются для совместимости. White labeling не меняет лицензию, юридические документы репозитория, исторические отчёты и уже записанные медиа.

## Эксплуатация и ошибки
Next.js читает DTO через внутренний API listener `/branding`. `FILEX_BRANDING_API_URL=http://api:9090/branding` установлен для web в Compose и offline production generator; default для запуска вне Compose — `http://127.0.0.1:9090/branding`. Адрес задаёт оператор, он не выводится из входящего Host. Listener нельзя публиковать наружу. При недоступности SSR за три секунды показывает нейтральное «Files»; клиент повторяет чтение и ADMIN видит сообщение о недоступности. При ошибке фонового refresh клиент сохраняет последнее полученное оформление.

Обновление включает обычный controlled upgrade до schema 18; возврат старого binary поверх новой schema запрещён существующим migration guard. [Upgrade runbook](controlled-upgrade.md). Production startup guard и внешняя приёмка остаются прежними.

## Проверки и дальнейшая работа
Negative/concurrency/fault тесты проверяют права, CSRF, reauth, недопустимые цвета/изображения, конкурентное сохранение, audit rollback, immutable PDF/mail и восстановление бренда. Browser сценарий проверяет draft/apply/conflict/reset, PNG assets, SSR без JavaScript, публичные страницы, разные темы, контраст и 320 px. Квалификация 2026-10-13 — [13 gates и source hash](history/white-label-evidence-2026-10-13.md); текущая задача — [session](session.md), общие команды — [testing](testing.md).

Ручная приёмка на реальных устройствах, пользовательские фирменные assets и независимый security review выполняются отдельно. Исторический [фото/видеотур](screen-tour.md) записан до появления этого редактора; он не является evidence настройки брендинга.
