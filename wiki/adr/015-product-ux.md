# ADR-015: интерфейс основных сценариев USER и ADMIN

## Контекст и проблема
Владелец запросил ревью и полноценную доработку удобства системы 2026-10-13. В текущем интерфейсе все ADMIN формы расположены подряд, Settings v1 редактируется только JSON, для reauth нужно уходить в другой раздел. В черновике формы переименования постоянно открыты, срок задаётся только числом, timezone вводится вручную. Получатель после server completion может видеть устаревшие кнопки (DEV-05).

## Решение
Сохранить существующий стек и brand-aware SVG. Сгруппировать навигацию по задачам и применить progressive disclosure: основной путь остаётся видимым, редкие настройки раскрываются. Добавить текстовые подписи к иконкам, пресеты и ползунок срока вместе с точным вводом, формы Settings v1 и понятные статусы. Подтверждение личности доступно внутри ADMIN. Деструктивное действие объясняет последствия до запроса.

## Поток данных и состояния
- USER draft → загрузка → проверка файлов/доступа → явный immutable publish → ссылки. Название сохраняется до открытия review; ожидаемая ревизия берётся из свежего ответа. Изменение полей закрывает review. Ошибка не очищает введённое.
- Settings: active value → локальные поля → полный draft → server validate → явное CAS apply. Переключение формы/JSON не теряет поля; JSON остаётся экспертным режимом. Ошибка validation/CAS не подменяется успехом. Смена origin/network сохраняет stop/restart/reconcile/reopen.
- Recipient: locked → available → downloading/resumable → unavailable при 401/403/404/410. Списки и старые download controls очищаются. Network/5xx сохраняют resume и показывают возможность повтора. Причина terminal denial не раскрывается; UI не утверждает fsync на диске получателя.
- Поиск POST: pending → results/empty/error; запоздалый ответ не заменяет более свежий фильтр. Raw search/секреты не записываются в URL.

## Threat model / architecture consistency / crypto review
Новые trust boundaries, permissions, cookies, persistence, crypto primitives и зависимости не вводятся. Клиентская валидация дополняет серверную; скрытая панель не является авторизацией. Confirm dialog не заменяет reauth, reason, dry-run, PG guards или audit. UI не показывает USER forensic/recipient correlation. Пароли/ключи не сохраняются в browser persistence.

Строгий compatibility gate запрещает добавлять даже выходные поля в прежний `Transfer`: клиенты используют additionalProperties=false. Поэтому добавлен owner-scoped `GET /api/v1/transfers/{id}/editor` с новым DTO `TransferEditor`, содержащим существующие detail-поля, `message` и `maxTtlSeconds`. Оба GET используют общий reader, owner check и `transfers:read`; старый ответ остаётся неизменным. `message` берётся из той же записи и нужен для сохранения сообщения при full metadata replacement. OpenAPI 3.1/types синхронизируются; AsyncAPI не меняется. Baseline и compatibility gate не ослабляются. Изменения UX не снимают production guard.

## Примеры и ограничения
Editor GET возвращает `maxTtlSeconds` из действующей Settings v1. Это несекретный предел публикации, а не новое разрешение: сервер повторно проверяет TTL при publish. Ползунок и пресеты ограничены этим пределом; точный ввод поддерживает весь диапазон от одной секунды. Единица ползунка выбирается так, чтобы предел был достижим с клавиатуры без округления: часы, затем минуты, иначе секунды. Начальный срок — минимум из суток и предела установки. При изменении политики во время работы review становится недоступен до исправления срока.

24 часа выбираются пресетом либо ползунком; точный ввод остаётся доступен клавиатуре. ADMIN настраивает MIME policy селектом и списком MIME, затем отдельно проверяет и применяет draft. Авто-apply опасных настроек отсутствует. Не вводятся tenancy, billing, обещания SLA или новая авторизация. Реальные AT/устройства/Windows и production приёмка остаются внешними.
